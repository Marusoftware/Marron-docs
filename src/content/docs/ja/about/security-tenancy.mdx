## Resource とポリシーを中心にした権限管理

固定ロールを大量に用意するのではなく、Resource の割り当てとポリシーを中心にアクセス制御します。権限はユーザーやグループに対し、Resource、Resource グループ、階層単位で付与できます。

操作権限は閲覧、作成、起動、停止、編集、削除などの粒度で定義します。ポリシーの継承と上書きを可能にしつつ、明示的な拒否や上位のセキュリティ制約は下位設定で解除できないようにします。

## 承認ルール

操作の種類、リスク、対象 Resource に応じて承認要否を決定します。例:

- VM の起動・停止: ポリシーにより即時実行または承認
- Resource の削除: 原則として承認を要求
- VLAN 変更: ネットワーク管理者の承認
- 物理サーバーの停止: 複数人承認など、より強い制御

承認フローでは承認者・承認グループ、複数承認、期限、却下・差し戻し、変更差分、監査記録を扱います。承認後に Plan が変更された場合、古い承認を流用しません。

## マルチテナント

将来の外部利用にも備え、テナント分離を基本モデルに含めます。初期の利用形態が単一環境であっても、Resource、API、データアクセス、バックアップ、Jam の権限、IPAM、作業チケット、監査ログでテナント境界を一貫させます。

標準は論理分離とし、より強い分離が必要な環境では専用 Core / Jam を配置できる余地を残します。

## Resource 割り当てとクォータ

テナントごとに CPU、メモリ、ストレージ、IP アドレス、ネットワークなどの割り当てと上限を管理できる設計とします。利用量の収集は将来のメータリングに利用できる形を目指しますが、課金機能は初期要件に含めません。

## Jam の権限

Jam は登録時に識別され、担当する Resource と許可された操作範囲を与えられます。Jam が Core の全権限を持つ設計にはしません。通信・認証情報の保護、鍵の更新・失効、権限縮小を設計上の必須課題とします。
