## バックアップとリストアを先に完成させる

高可用性やデータベースレプリケーションより先に、確実なバックアップと復元を実装します。バックアップファイルを作れるだけでなく、実際に復元できることを検証します。

バックアップ対象には次を含めます。

- Resource と Relation
- IPAM、Desired / Observed State の永続化データ
- テナント、ポリシー、権限
- マップのレイアウト
- 作業チケット、承認、監査ログ
- Jam の登録情報と設定
- プラグイン設定
- 必要な秘密情報・証明書 (暗号化とアクセス制御を前提とする)

手動・定期バックアップ、世代管理、保持期間、暗号化、オフサイト保管、整合性検査、復元テストを段階的に整備します。

## 障害時の動作

Core と Jam の通信が途絶えた場合でも、Jam は事前に許可された範囲で監視や限定的なローカル処理を継続できます。再接続時には差分を同期します。

ただし、ネットワーク分断時に競合する変更操作を無制限に許可しません。操作リース、フェンシング、冪等性、必要に応じた Quorum などにより二重実行や競合を防ぎます。

冗長性を評価するときは、同じ電源、ラック、スイッチ、拠点に属するノードを独立した冗長系と誤認しないよう、障害ドメインを扱います。

## 段階的なロードマップ

### Phase 1: 基盤

- 単体 Core と Jam 登録
- Resource / Relation モデル
- Discovery と基本的な Observed State
- 統合インフラマップの基礎
- 認証・ポリシー・監査
- バックアップとリストア

### Phase 2: 安全な運用

- Desired State と差分表示
- Plan / Preview / Apply
- 承認ワークフロー
- 手動作業チケットとメンテナンス管理
- IPAM、ラック図、物理配線の拡張
- プラグイン API の整備

### Phase 3: 分散・自動化

- Jam 間 P2P とローカル集約
- Observer / Worker / Autonomous の制御
- テナントごとのクォータ
- プラグインの外部プロセス化
- 障害ドメインと分断時の制御

### Phase 4: 可用性の拡張

- Core HA / クラスタ
- データベースレプリケーション
- Core フェイルオーバー
- より高度な復旧・運用機能

これは実装の優先順位を示すものであり、各機能の詳細仕様やリリース時期を確定するものではありません。
