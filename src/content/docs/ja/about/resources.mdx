## 共通 Resource と詳細データ

Marron では、物理サーバー、ネットワーク機器、インターフェース、IP アドレス、ネットワーク、仮想マシン、ストレージ、サービスなどを共通の **Resource** として識別します。

共通 Resource は ID、種別、名前、所属、ライフサイクル、共通メタデータなどを保持します。機器種別固有の属性は詳細テーブルに分離し、共通テーブルが巨大化することを避けます。

データモデルは概念上、次の領域に分けます。

- Resource identity / metadata
- 種別ごとの詳細データ
- Resource 間の Relation
- Desired State / Observed State
- ポリシー、テナント、権限
- 履歴、監査ログ、作業チケット
- マップごとのレイアウト情報

## Relation

Resource 同士の関係は独立した Relation として表現します。例:

- サーバーに NIC が搭載されている
- NIC とスイッチポートが物理ケーブルで接続されている
- IP アドレスが NIC に割り当てられている
- VM が物理サーバー上で稼働している
- VM がストレージに接続されている
- スイッチポートに VLAN が設定されている

物理接続と論理接続は別の関係種別です。必要に応じてケーブル、パッチパネル、ポート番号、接続経路などの情報を追加します。

## 状態の分離

ライフサイクルと稼働状態は別々に管理します。

| 分類 | 例 |
| --- | --- |
| Lifecycle | Planned、Discovered、Registered、Managed、Unmanaged、Retired |
| Runtime health | Online、Offline、Degraded、Unknown、Maintenance |

さらに、設計上のあるべき状態である **Desired State** と、実際に観測された **Observed State** を分離します。観測値には取得元、取得時刻、鮮度を持たせ、古い値を現在の事実として誤認しないようにします。

## データ保存方針

Resource の基本情報と高頻度テレメトリは同じ場所に詰め込みません。時系列データは専用の保存先と保持期間を設け、Resource Registry の肥大化を防ぎます。

リレーショナルな関係を基本とし、柔軟性が必要な属性に限って JSONB などを選択します。UUID を識別子の候補とします。PostgreSQL を本番向け候補、SQLite を軽量な開発・単体利用向け候補としますが、最終的な対応範囲は別途決定します。

## IPAM

IP アドレス管理 (IPAM) は Marron の標準機能として提供する方向です。アドレス、サブネット、VLAN、割り当て状況を Resource / Relation と整合させます。NetBox など外部 IPAM との連携は将来の任意統合とし、必須依存にはしません。

## マップとの関係

座標や表示位置は Resource 本体に保存せず、マップ・ビューごとのレイアウトデータとして分離します。同じ Resource を物理配線図、ラック図、論理ネットワーク図など複数のビューに異なる位置で表示できます。
